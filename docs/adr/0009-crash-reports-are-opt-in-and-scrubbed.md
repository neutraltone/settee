# Crash reports are opt-in and scrubbed

_Partly replaced by [ADR 0010](0010-crash-reports-also-carry-service-failures-slow-journeys-and-error-reports.md), which also reports Settee's own service failures and Slow Journeys, and errors on screen that could be Settee's, a Provider's failures among them. Everything else here still holds._

Settee used to promise that it collected nothing: no crash reporter, no telemetry. But a crash or a freeze on a viewer's Fire TV Stick went unnoticed unless they mentioned it, and even then there was no stack trace or app version to fix it from. Bugs that only show up on a real stick, with a real Provider and 1 GB of memory, stayed invisible. So Settee now sends Crash Reports to Sentry (#570). It keeps as much of the old promise as reporting allows, and these rules are why the change is acceptable at all:

- **Off until the viewer turns it on.** Nothing is sent by default. A viewer can turn reports on in three places only: the last step of Setup, after the OpenSubtitles step, where "Not now" has the Highlight so pressing OK through never opts anyone in; Settings → Privacy, where they can also turn it off again; and the question asked the next time Settee opens after a crash or freeze it held (Send, Don't send, Always send). Two Don't sends and that question stops being asked. The choice belongs to the device, so it isn't synced and doesn't change between Profiles. Turning it on anywhere sends a crash held while it was off, since saying yes covers that one too, as Always send does. Turning it off throws away anything held or waiting to go: nothing queued is sent on the way out.
- **An allow-list decides what leaves the device, not a deny-list.** A report has the app version, the Android or Fire OS version, the device model, free memory, the route name of the screen that was open (never its arguments), a random install id and the stack trace. Every other tag, extra, context and breadcrumb is removed in the SDK's before-send and before-breadcrumb hooks, so this also covers anything a later SDK version adds. In what's left, URLs lose their host, login, query string and fragment, and anything shaped like a MAC is masked.
- **Nothing about Providers, Profiles or what's watched ever leaves the device.** No Provider address, username, password or MAC; no Provider, Profile or channel names; no titles. Sentry is set not to store IP addresses. Provider failures (HTTP errors, dead streams, panels returning web pages) are never reported, and of handled errors only a closed list that only Settee's own code can cause is. (ADR 0010 changes this: Settee's own services' failures and Slow Journeys are reported too, and a Provider failure the viewer was shown leaves the device as an Error Report, with crash reports on or when they choose to send it.)
- **Only official release builds can send.** The Sentry DSN is built in from a CI secret, the same way as the TMDB Key. Debug builds, forks and anyone's build without the key have no DSN, and in those builds crash reporting doesn't exist: no SDK starts, and the viewer is never asked.

Loosening any of these, such as turning reports on by default, adding a field to the allow-list, reporting Provider failures or letting another build send, needs a new ADR that replaces this one.

We turned down three alternatives:

- **On by default, with a way to opt out.** It would catch more crashes, but it would quietly break a promise Settee had published, and a viewer who never opens Settings would never know.
- **Redacting reports the way Diagnostics does.** Settings → Diagnostics' report removes the Provider addresses and logins it recognises (`diagnostics/Redaction.kt`), which is fine for a file saved to the viewer's own NAS. A crash report goes to a third party, and the next leak is usually something nobody thought to look for, so only what's listed may leave.
- **Self-hosting Sentry or GlitchTip.** It would keep reports off a third party's servers, but Settee never runs a server of its own.

## Consequences

- `core/CrashReports` and its own helpers in `core/` (`CrashScrubbing`, `HeldCrash`) are the only code that imports Sentry's SDK, and nothing outside `core/` does (`CrashReportsBoundaryTest`). Screens, view models and `OpenTvApp` go through it, so a rule changes in one place.
- Sentry's transport gate reads the consent as each envelope's turn to go comes, so an envelope still queued when reports are turned off stays behind, and is deleted with the rest of Sentry's cache. Sentry's markers of which Android exit records it has looked at are kept.
- Sentry reads Android's exit history when it starts (Android 11 and later). It reports only the newest freeze, never older ones or the raw thread dump, and `beforeSend` drops any freeze or crash from that history that happened before reports were last turned on, so one from while they were off, even one answered Don't send, never leaves.
- A held crash keeps the allow-listed details that belong to its moment (the screen's route name, free memory, the Android version and Settee's build), and its report sends those, not the sending launch's.
- Of Xtream parse failures, only a reply that is whole JSON Settee couldn't read is reported. One that breaks off part way is the Provider's, like a web page.
- The SDK is started by hand, never by its auto-init content provider, so nothing runs before Settee has checked the DSN and the viewer's choice. Performance tracing, profiling, session replay, screenshots, view hierarchy, interaction, network and logcat breadcrumbs, and `sendDefaultPii` all stay off.
- The scrubber's tests send Xtream-, M3U- and Stalker-shaped URLs and a MAC through the module, with a fake transport in place of Sentry's, and check what would have left the device. A change that leaks a credential fails CI.
- A DSN can always be pulled out of an APK. It can only send, and what limits misuse is Sentry's spike protection and a rate limit on the key (30 events an hour). Sentry can't keep only Settee's published releases: its release filter only blocks versions matching a pattern, so a fake release is blocked by pattern once it shows up, and an abused key can be revoked and a new one built into the next release (#571).
- Sentry also holds, per release, the commits that went into it, sent by `release.yml` (#622). That's the repo's own public history, nothing from a viewer. Release health (crash-free sessions) stays off: it would send a session on every launch, which is the usage tracking this ADR rules out.
- The daily routine that files GitHub issues from Sentry writes each issue in its own words and never pastes an event, so if the scrubber ever misses something, it still doesn't end up in a public issue.
- `docs/PRIVACY.md` lists what a report contains and what it never contains, and has to change whenever the allow-list does.

## Decisions made while building it

- **Back on the after-crash question isn't an answer.** It closes the question, and it's asked again at the next launch. It doesn't count as a Don't send, since the viewer said nothing.
- **Setup skips its Crash Reports step on a device that already has reports on**, such as one where they were turned on from the after-crash question before Setup finished. There's nothing left to offer.
- **What reports cost at launch while they're off.** The spec asked for nothing beyond reading a setting and checking for a held crash. Holding crashes and freezes costs a little more, and we accept it, since without it nothing that happens while reports are off could ever be asked about:
  - an uncaught-exception handler, installed in `OpenTvApp.onCreate` (one static field written; Sentry itself doesn't start);
  - on Android 11 and later, a read of Android's exit history for a freeze since the last look, on a background thread, so the main thread only checks for the held file;
  - before Android 11, which includes the Fire TV Stick (Fire OS 7, API 28), there's no exit history to read, so a `FreezeWatch` daemon thread watches instead. It's posted to the main thread behind the launch's own work, starts by sleeping, and then wakes every 5 seconds to post one empty message to the main thread. It stops once reports are turned on, when Sentry's own watchdog takes over.
